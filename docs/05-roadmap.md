# 구현 순서

현재 완료 범위는 설계 문서, data/와 src/ 안내, .env.example과 .gitignore를 포함한 저장소 기본 구조다. 아래는 향후 구현 순서이며 이미 개발된 기능 목록이 아니다. 일정은 역량과 가용 시간 확인 후 산정한다.

| 단계 | 만들 것 | 다음 단계로 넘어가는 조건 |
| --- | --- | --- |
| 0. 도메인 확인 | 운영자 업무 인터뷰 2~3회, 합성 미션과 체크리스트 | 실제 검수 항목과 가장 큰 반복 부담 확인 |
| 1. 화면과 상태 | Studio/Mission, 정적 조직도, 합성 이벤트 재생 | 근거 확인·수정 요청·승인 흐름을 사람이 이해 |
| 2. 단일 실행 | 입력 버전, DB, 단일 에이전트 기준선 | 저장·중단·복구와 출력 계약 확인 |
| 3. 역할 분리 | Story/Audience/Campaign/QA, 제한된 계획 | 한 미션의 패키지가 끝까지 만들어짐 |
| 4. 운영 제어 | 선택적 재작업, 예산, 승인, Audit | 중복·오래된 승인·장애 복구 검증 통과 |
| 5. 비교 평가 | 단일/고정/멀티 비교 | 품질·비용·검토 시간 차이를 설명 가능 |
| 6. Agent Lab | 후보 비교와 설정 활성화·롤백 | 검증 미달 후보 활성화 방지 |
| 7. 공개 데모 | 읽기 전용 데모, 영상, 평가 보고 | 합성/실행/재생 구분과 인증 경계 확인 |

## MVP 완료 정의

- 운영자가 입력을 고정하고 실행 예산을 설정할 수 있다.
- 한 회차의 검토 보고서와 홍보 문안을 근거와 함께 생성한다.
- 실패한 문안 수정 시 독립적인 분석 결과는 재사용한다.
- 프로세스를 재시작해도 승인 대기 상태와 산출물이 유지된다.
- 승인된 정확한 패키지만 내보낼 수 있다.
- 실행 비용·실패·사람 개입을 감사 이력에서 설명할 수 있다.
- 단일 에이전트 기준선과의 비교 결과가 있다.

Agent Lab 전체 구현과 별도 CEO 콘솔은 MVP 종료 조건에 포함하지 않는다.

## 가장 먼저 검증할 질문

1. 운영자는 설정 검토, 홍보, 독자 분석 중 어디에서 실제 시간을 가장 많이 쓰는가?
2. 설정집이 정리되지 않은 상태에서도 이 도구가 도움이 되는가?
3. 근거와 변경점이 보이면 승인 시간이 줄어드는가?
4. QA가 유용한 오류를 발견하는가, 오탐을 추가하는가?
5. 역할 분리가 고정 워크플로보다 충분한 가치를 만드는가?

## 위험과 축소 전략

| 위험 | 대응 |
| --- | --- |
| 역할만 많고 품질 차이가 없음 | 단일/고정 기준선에 따라 역할 통합 |
| 도메인 판단이 피상적임 | 현업 체크리스트와 사람 검수, 자동 확정 축소 |
| 그림 생성까지 범위가 확장됨 | 텍스트 공개 준비 패키지에 우선 집중 |
| 검토자가 오탐 처리에 더 오래 걸림 | 오류 심각도와 확실한 근거 우선, 보류 표현 |
| 합성 데모만 잘 작동함 | 실제 자료 도입 전 별도 허가와 비공개 평가 |
| 채용 기능이 모델 선택 UI에 그침 | 역할별 실패·회귀·롤백까지 검증할 때 확장 |

## 저장소의 다음 변화

구현을 시작하면 문서에 대응하는 issue를 만들고, 각 단계에서 확인한 사실과 바뀐 설계 결정을 기록한다. data/와 src/에는 현재 안내 문서만 둔다. .env.example에는 실제 키 없이 설정 계약 초안을 기록한다. 실행 코드, 의존성 파일, 테스트와 배포 설정은 구현 단계에서 추가한다.
